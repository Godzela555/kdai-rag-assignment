```
เอกสาร .md (4 บทความสุขภาพจาก MedThai)

   │  LLM เขียน "context" สั้น ๆ ให้แต่ละ chunk (Anthropic Contextual Retrieval)
   ▼
┌──────────────────────────┐   ┌──────────────────────────┐
│ BM25 index               │   │ Vector index             │
│ standard analyzer        │   │ bge-m3 (1024 มิติ)        │
└────────────┬─────────────┘   └────────────┬─────────────┘
             └──────── RRF รวมอันดับ ────────┘
                          │ top 5 chunks
                          ▼
                    LLM สร้างคำตอบ
```

## ปัญหาที่พบในระบบเดิม

### ปัญหาที่ 1: BM25 ตัดคำภาษาไทยไม่ได้

BM25 index ใช้ `standard` analyzer ซึ่งแยกคำด้วยช่องว่าง แต่ภาษาไทยไม่เว้นวรรคระหว่างคำ ทั้งประโยคจึงกลายเป็น "คำเดียว"

```
standard → ['อาการของหัดเยอรมัน']        ← คำเดียวยาว ๆ ไม่ตรงกับอะไรใน index
thai     → ['อาการ', 'หัดเยอรมัน']        ← ตัดเป็นคำจริง
```

ผลคือ BM25 หาไม่เจอเลย **22 จาก 24 คำถาม** (ชุดทั่วไป) และ **13 จาก 20 คำถาม** (ชุดเจาะลึก) ทั้งระบบจึงพึ่ง vector search ฝั่งเดียว แม้จะเรียกว่า hybrid ก็ตาม

### ปัญหาที่ 2: RRF ไม่ได้อ่านเนื้อหา

RRF ให้คะแนนจาก "ลำดับ" ของแต่ละระบบเท่านั้น (`1/(60+rank)`) ไม่ได้ดูว่าเนื้อหาตอบคำถามจริงหรือไม่ เมื่อคำตอบเป็นข้อเท็จจริงเฉพาะที่ซ่อนอยู่กลาง chunk ยาว ๆ chunk ที่ถูกต้องจึงอาจไม่ได้อยู่อันดับ 1

## ระบบที่ปรับปรุง (2)

```
คำถาม
  ├─► BM25 (thai analyzer)  ──► 10 อันดับ ─┐
  └─► Vector (bge-m3)       ──► 10 อันดับ ─┴─► RRF ─► ผู้สมัคร 10 chunks
                                                         │
                       แบ่งแต่ละ chunk เป็นหน้าต่าง ~500 ตัวอักษร
                                                         │
                 Cross-encoder (bge-reranker-v2-m3) ให้คะแนน (คำถาม, หน้าต่าง)
                       คะแนน chunk = คะแนนหน้าต่างที่ดีที่สุด (MaxP)
                                                         │
                                                  top 5 chunks
                                                         ▼
                                       LLM ตัวเดิม สร้างคำตอบ
```

### (A) Search algorithm: Thai BM25 — `improved_ingest.py`

- สร้าง index ใหม่ `improved-bm25-index-thai` ที่ใช้ `thai` analyzer (มีในตัว OpenSearch ไม่ต้องติดตั้งเพิ่ม)
- คัดลอก chunks และ context **ชุดเดียวกับระบบเดิมทุกตัวอักษร** ด้วย `_reindex` จึงเปรียบเทียบได้ยุติธรรม (ต่างกันแค่วิธีตัดคำ)
- ไม่แก้ไฟล์เดิม ระบบ (1) ยังรันได้เหมือนเดิม

### (B) Reranking: Cross-encoder แบบ MaxP — `improved_search.py`

**ทำไมต้อง reranker:** bge-m3 (bi-encoder) แปลงคำถามกับเอกสารเป็น vector *แยกกัน* แล้ววัดความใกล้ ส่วน cross-encoder อ่านคำถามกับเอกสาร *พร้อมกัน* ทุกคำ จึงตัดสินได้แม่นกว่าว่าตอบคำถามจริงหรือไม่ แลกกับความช้า จึงใช้กับผู้สมัครแค่ 10 อันดับที่ค้นมาแล้ว

**ทำไมเลือก `BAAI/bge-reranker-v2-m3`:** บทความ Jev reranker ที่อาจารย์แนะนำใช้รุ่นนี้เป็นตัวเทียบ และรายงานว่าได้ผลใกล้เคียงกัน แต่ Jev ต้องใช้ API key แบบเสียเงิน ส่วน bge-reranker-v2-m3 รันในเครื่องได้ฟรี รองรับภาษาไทย และเป็นตระกูลเดียวกับ bge-m3

**ทำไมต้อง MaxP (บทเรียนจากการทดลอง):** ครั้งแรกส่งทั้ง chunk ให้ reranker ผลกลับ *แย่ลง* ในบางข้อ เพราะเราตั้งให้ reranker อ่านได้ครั้งละ 512 tokens (`max_length=512` ใน `improved_search.py` เพื่อให้รันบน CPU ได้เร็วขึ้น ตัวโมเดลเองรองรับได้ถึง ~8,000 tokens) แต่ chunk ของเรายาวได้ถึง 22,970 ตัวอักษร (doc_48 ในตัวอย่างนี้ยาว 8,404) ส่วนท้ายจึงถูกตัดทิ้ง เช่นคำถาม *"คนเป็นกรดไหลย้อนควรเลี่ยงซอสมะเขือเทศกับกระเทียมไหม"* คำตอบอยู่กลาง doc_48 ซึ่ง reranker มองไม่เห็น จึงจัด chunk นี้ไว้อันดับ 5

วิธีแก้คือแบ่ง chunk เป็นหน้าต่างละ 500 ตัวอักษร (ซ้อนกัน 100 ตัวอักษร) ให้คะแนนทุกหน้าต่าง แล้วใช้คะแนนสูงสุดเป็นคะแนนของ chunk (MaxP, Dai & Callan 2019) chunk ที่ส่งให้ LLM ยังเป็น chunk เต็มเหมือนเดิม

## (3) ผลการวัด: ต่างกันตรงไหน ดีขึ้นอย่างไร เพราะอะไร

### วิธีวัด

วัดส่วน **ค้นหา (retrieval)** เพราะ LLM ตัวเดิมจะตอบถูกได้ก็ต่อเมื่อได้ chunk ที่มีคำตอบ ใช้คำถาม 2 ชุด ทุกข้อกำหนด chunk ที่ถูกต้องไว้ *ก่อน* รันการค้นหา

- **ชุดทั่วไป 24 ข้อ** (`eval/eval_questions.json`): คำถาม 4 ข้อของอาจารย์ + ถามตามหัวข้อบทความ คำตอบกำหนดจากหัวข้อของ chunk
- **ชุดเจาะลึก 20 ข้อ** (`eval/eval_questions_hard.json`): ถามข้อเท็จจริงเฉพาะ เช่น ชื่อยา ตัวเลข ปี พ.ศ. คำตอบ = ทุก chunk ที่มีวลีนั้นอยู่จริง (ให้โปรแกรมหา ไม่ได้เลือกเอง)

ตัวชี้วัด (จาก 5 chunks ที่ส่งให้ LLM):
- **Hit@1** = อันดับ 1 ถูกไหม, **Hit@5** = มีตัวถูกใน 5 อันดับไหม
- **Recall@k** = ใน k อันดับแรก เจอ chunk ที่ถูกต้อง*ครบ*กี่ส่วน เช่น ข้อที่มีคำตอบอยู่ 2 chunks แล้วเจอ 1 ใน top-3 ได้ Recall@3 = 0.5 (มี 12 จาก 44 ข้อที่คำตอบอยู่หลาย chunk ข้อแบบนี้ Recall@1 จึงได้เต็ม 1.0 ไม่ได้)
- **MRR@5** = ค่าเฉลี่ย 1/อันดับของตัวถูกตัวแรก (1.0 = อันดับ 1 ทุกข้อ)

**ชุดเจาะลึก (20 ข้อ)** — ข้อเท็จจริงเฉพาะที่ซ่อนอยู่กลาง chunk ยาว

|---|---|---|---|---|---|---|---|---|
| (1) ระบบเดิม | 0.75 | 1.00 | 0.688 | 0.950 | 0.975 | 0.850 | 13/20 | 0.2 |

| **(2) ระบบใหม่: Thai BM25 + Reranker แบบ MaxP** | **1.00** | **1.00** | **0.912** | **0.963** | **0.988** | **1.000** | **0/20** | 14.9 |

**ชุดทั่วไป (24 ข้อ)** — ถามตามหัวข้อบทความ

|---|---|---|---|---|---|---|---|---|

ผลรายคำถามทั้งหมดอยู่ใน [`eval/eval_results.md`](eval/eval_results.md)

**อ่านค่า Recall:** ชุดเจาะลึก ระบบใหม่เจอ chunk ที่ถูกตั้งแต่อันดับ 1 มากขึ้นชัดเจน (Recall@1: 0.688 → **0.912**) และใน 5 อันดับเจอครบเกือบทุกข้อ (Recall@5: 0.975 → 0.988) ส่วนชุดทั่วไป Recall@1 ลดลง (0.812 → 0.750) จากข้อ q03, q04 แต่ Recall@3 กลับดีขึ้น (0.917 → **0.958**) เพราะ reranker ดึง chunk คำตอบตัวที่สองของข้อที่มีคำตอบหลาย chunk ขึ้นมาไว้ใน 3 อันดับแรก (q02, q12) ที่แย่ลงก็มี: q04 คำตอบตัวที่สอง (doc_1) หลุดจาก 5 อันดับ (Recall@5: 1.0 → 0.5) และ h04 คำตอบตัวที่สองหลุดจาก 3 อันดับแรก

Recall@1 และ Recall@3 คิดจากอันดับที่บันทึกไว้ใน `eval_results.json` ด้วย `python eval/evaluate.py --rescore` (ไม่ได้ค้นหาใหม่ ตัวเลขอื่นทุกตัวเหมือนเดิม)

### สรุปความแตกต่าง

| | ระบบเดิม (1) | ระบบใหม่ (2) | ผล |
|---|---|---|---|
| ตัดคำ BM25 | `standard` (ตัดที่ช่องว่าง) | `thai` (ตัดด้วยพจนานุกรม) | BM25 หาไม่เจอ: 35/44 ข้อ → **0/44 ข้อ** |
| จัดอันดับขั้นสุดท้าย | RRF (ดูแค่ลำดับ) | RRF → cross-encoder อ่านคำถามคู่กับเนื้อหา | คำถามเจาะลึก อันดับ 1 ถูก 75% → **100%** |
| chunk ยาว | — | ให้คะแนนเป็นหน้าต่าง 500 ตัวอักษร (MaxP) | แก้ปัญหา reranker มองไม่เห็นท้าย chunk (h02, h18: อันดับ 5 → 1) |
| ความเร็ว | ~0.2 วินาที/คำถาม | ~14 วินาที/คำถาม (CPU) | ช้าลง เป็นราคาของความแม่นยำ |

**ดีขึ้นตรงไหน:** คำถามเจาะลึก (ถามชื่อยา ตัวเลข ปี พ.ศ.) ระบบใหม่จัด chunk ที่มีคำตอบไว้อันดับ 1 **ครบทั้ง 20 ข้อ** (เดิม 15 ข้อ) ดีขึ้น 5 ข้อ ไม่มีข้อไหนแย่ลง

**เพราะอะไร:**
1. **Thai BM25** ทำให้ BM25 ใช้งานได้จริง คำเฉพาะอย่าง "เอลเทอร์", "โพแทสเซียม", "5 วัน" ถูกจับคู่ได้ตรงตัว ซึ่ง vector search ที่ดู "ความหมายรวม" มักพลาด ระบบจึงกลับมาเป็น hybrid จริง
2. **Reranker** อ่านคำถามกับเนื้อหาพร้อมกัน จึงแยกได้ว่า chunk ไหน *ตอบ* คำถาม ไม่ใช่แค่ *พูดเรื่องเดียวกัน* เช่น h09 (หูหนวกกี่ %) ระบบเดิมจัด doc_3 ไว้อันดับ 3 เพราะ doc_6 ก็พูดเรื่องทารกพิการ แต่ reranker เห็นว่า doc_3 มีตัวเลข 58% จริง
3. **MaxP** จำเป็นมาก ถ้าไม่ทำ (แถว 2B) reranker กลับทำให้ 2 ข้อแย่ลงเหลืออันดับ 5 เพราะมองไม่เห็นคำตอบที่อยู่ท้าย chunk

**ที่ไม่ดีขึ้น (รายงานตามจริง):** ชุดทั่วไป ระบบเดิมได้เต็มอยู่แล้ว ระบบใหม่พลาดไป 2 ข้อ (q03, q04) โดย chunk ที่ถูกต้องตกไปอยู่อันดับ 2 แต่ยังอยู่ใน 5 chunks ที่ส่งให้ LLM (Hit@5 = 1.00 ทุกระบบ) LLM จึงยังได้ข้อมูลครบ เมื่อดูแล้ว chunk ที่ขึ้นมาอันดับ 1 (doc_1 บทนำโรค) ก็เกี่ยวข้องกับคำถามจริง แค่ไม่ใช่ chunk ที่กำหนดไว้

**สรุป:** คำถามกว้าง ๆ ระบบเดิมก็พอ แต่คำถามที่ต้องการข้อเท็จจริงเฉพาะ ซึ่งเป็นสิ่งที่ RAG ทางการแพทย์ต้องตอบให้ถูก ระบบใหม่แม่นกว่าชัดเจน แลกกับเวลาที่เพิ่มขึ้น (ถ้ามี GPU จะเร็วขึ้นมาก)

### ข้อจำกัดที่พบ (ทำต่อได้)

- **Context ของ Anthropic ยังไม่ได้ใช้เอกสารเต็ม:** ในโค้ดเดิม `full_doc_content = doc.page_content` ทำให้ LLM เห็นแค่ chunk ตัวเอง ไม่ใช่ทั้งบทความ ซึ่งต่างจากแนวคิด Contextual Retrieval แต่ถ้าส่งบทความเต็ม (~60KB ภาษาไทย) ทุก chunk จะเกินโควตา Groq ฟรี (8,000 tokens/นาที) จึงไม่ได้แก้ในงานนี้
- **Chunk ยาวไม่เท่ากัน:** MarkdownNodeParser ไม่ได้ใช้ `chunk_size=256` จริง แบ่งตามหัวข้ออย่างเดียว chunk จึงยาวตั้งแต่ 258 ถึง 22,970 ตัวอักษร (เฉลี่ย 4,465) การแบ่ง chunk ใหม่ให้สั้นลงน่าจะช่วยได้อีก
- **ชุดคำถามเล็ก (44 ข้อ):** ผลบอกแนวโน้มได้ แต่ยังไม่ใช่การวัดที่ใหญ่พอจะสรุปทางสถิติ
